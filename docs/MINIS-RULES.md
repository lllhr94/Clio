# Open Minis 的手感规则，Clio 该学哪些（2026-11-21）

来源：Open Minis 公开仓库 `src/ios/MinisTests/Standalone/`，322 个测试文件，开头注释写了 233 条规则（`[T-…]` 标签）。每条都写了用户怎么反馈、为什么这样定。这里只读注释、学思路，GPL 代码不抄。

过了一遍，和模型服务商、崩溃符号、备份、日历这些无关手感的不列。剩下和 Clio 有关的按「多影响手感」排。主人在「要不要」一列勾选，没勾的不做。

状态：✅ Clio 已有或已改 · 🔨 这次 Claude 顺手改了 · ⬜ 没有

## 一、滑动和掉帧（最影响手感）

| # | Minis 规则 | 它为什么这样做 | Clio 现在 | 建议 | 要不要 |
|---|---|---|---|---|---|
| 1 | `[T-composer-typing-lag]` 每次重画都要查的文字，先记住结果 | 实测打字卡顿：每个字都要重画聊天页，查翻译文字占了主线程两成 | 🔨 `Words.t`（老书卷名换新名）每次重画都逐字扫一遍，已改成记住结果；`L.t` 本来就是查表 | 再查 `ChatPage` 里每次重画都会跑的循环（`sources(for:)` 每条回复都从头找一遍） | |
| 2 | `[T-scroll-sync-defer]` 手指在滑的时候，后台来的刷新先攒着，停了再做 | 滑动中正好有同步刷新，首页两千行重算，掉帧 | ⬜ 旅伴在别的对话干活、首页刷新都会在你滑的时候插进来 | 聊天页报告「正在滑」，期间首页、侧栏、别的对话的刷新延后到停手 | |
| 3 | `[T-scroll-first-build-once]` 回复第一次出现时直接给高度，不要量两遍 | 长回复每条多花 40～65 ms | ⬜ SwiftUI 自己量 | 给每条回复按内容记住高度（`[T-ios-listsessions-perf]` 的「按内容记高度、有上限」） | |
| 4 | `[T-stream-end-scroll-overlap]` / `[T-stream-precalc-freeze]` 回复写完那一刻高度一次长很多，别盖住下面 | 用户正在滑时回复写完，字压到别的行上 | ⬜ 未见报，留意 | 写完时不动你正在看的位置 | |
| 5 | `[T-new-session-first-block-jump]` 新对话第一条回复出现时整页跳一下 | 「正在想」那行换成正文那一帧，整页上跳 18 点 | ⬜ Clio 也有「已递出，等它开口」→ 正文的切换 | 占位行和正文同高过渡 | |
| 6 | `[T-send-composer-shrink-absorb]` 发出消息后输入框变矮，聊天先上跳再下落 | 录屏里上 48、上 70、再一下掉 106 | ⬜ Clio 发消息时输入框也会缩 | 新消息正好填上输入框让出来的空，上面的不动 | |
| 7 | `[T-rotate-scroll-jank]` 转屏后往上翻会跳 | 转屏把所有记住的高度清掉了 | ⬜ iPad / 横屏时可能有 | 宽度变了只重算看得见的 | |
| 8 | `[T-skill-zip-off-main]` 一轮做完时整个 App 冻一下 | 打包技能在主线程 | ⬜ Clio 一轮结束时也会写快照、存对话、整理记忆 | 一轮结束的收尾全部挪到后台（并进 C24） | |
| 9 | `[T-storage-session-cache]` 存储页每次打开都把整个文件夹扫一遍 | 慢 | ⬜ 养护页一样（`CarePage` 算占用） | 一次进入只扫一次，改了哪个只重算哪个（并进 C24） | |

## 不学的

- 模型服务商兼容（Anthropic / Codex / Gemini / DeepSeek 等几十条）：Clio 的服务商层另有做法，出问题再查对应条。
- 崩溃符号、日志、Mac Dock 角标、iCloud 迁移、备份墓碑、子代理生命周期：和手感无关或 Clio 没有这功能。
